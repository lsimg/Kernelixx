# Kernelixx

[Подробно: что было и что стало](docs/MIGRATION_V2.ru.md) ·

Kernelixx — программа для терминала, которая проверяет, можно ли запускать
готовую нейросеть быстрее и с меньшим расходом памяти, сохраняя её результаты.
Она измеряет исходную модель, пробует доступные преобразования, проверяет ответы
и сохраняет отчёт. Если подходящего улучшения нет, остаётся исходная модель.

Проект предназначен для инженерных экспериментов и воспроизводимых измерений.
Веб-сайта, графического приложения и сервера в нём нет. Картинки с результатами —
обычные сохранённые файлы отчёта, которые можно открыть отдельно.

## Модернизация V2

Добавлены потоковые данные и численная валидация, раздельные метрики RSS/CUDA
allocated/reserved, ограниченный поиск цепочек, независимые парные запуски и
экспорт с настоящей повторной загрузкой. Одиночное ускорение не заменяет baseline:
нужны минимум три пары с улучшением в каждой. Неоднозначный результат получает
статус `INCONCLUSIVE`.

Проверено локально: 127 тестов; RAM всего эксперимента ResNet50 снизился на 8,83%
на CPU и 4,60% в CUDA-сценарии, ответы на 200 размеченных изображениях сохранены.
Это память процесса в RAM; снижение расхода VRAM этим сравнением не установлено.
GPU-тайминги нестабильны: ускорение steady-state не подтверждено. В отдельном
синтетическом CPU-тесте ResNet18 цепочка ONNX дала медиану ускорения 2,53×
в трёх независимых парах с проверкой численной корректности и дрейфа.
Последующий пользовательский запуск дал 2,45× по трём отдельным парам и успешно
проверенный экспорт. Его результаты сохранены [отдельно](docs/experiments/manual-demo-20261108.json).

[Подробное сравнение с предыдущей версией](docs/MIGRATION_V2.ru.md) содержит схемы
старого и нового пути, объяснения всех изменённых модулей, результаты и цену
дополнительных проверок. ONNX уже существовал: обновление улучшает управление
памятью и надёжность выбора, а не обещает универсальное ускорение любой модели.

```bash
python -m pip install -e ".[onnx,memory,dev]"
python -m kernelixx profile-memory --model resnet18 --device cuda
python -m kernelixx optimize-pipeline --model resnet18 --device cpu --pipelines onnx onnx+quantization --trials 3 --output results/pipeline
python -m kernelixx benchmark-repeat --model resnet18 --device cuda --pipeline fp16 --trials 3
python -m kernelixx optimize-llm --model-file model.gguf --threads 1 4 --prompt-format auto --n-batch 256 --n-ubatch 64 --validate-logits
python -m kernelixx export --run-dir results/pipeline/latest --output results/exported-model
```

У каждой команды есть `--help`. Старые команды сохранены. Для больших наборов
подходят NPZ или каталог с `inputs.npy` (float32) и `labels.npy` (int64).
Размер batch задаёт `--input-shape`, численных блоков — `--validation-chunk-elements`.
Порядок данных и последний неполный batch сохраняются. Нужен запас временного диска.

RSS — память всего процесса; sampling может пропустить короткий пик. CUDA
allocated/reserved и полный VRAM процесса — разные величины. Недоступные
источники возвращают `null`.

GGUF использует шаблон из метаданных, отдельно измеряет prompt processing и
decode, проверяет prompt-logits и задания с `expected_exact`. Локальная сборка
llama.cpp поддерживает CPU: GPU offload остаётся `NOT VERIFIED`. Совпадение
токенов не доказывает качество ответов. Форматы KV-cache требуют реальной
проверки с выбранной моделью и backend.

## Что уже работает

- ResNet18, ResNet50 и пользовательские модели через Python-фабрику.
- Анализ параметров, размера весов, времени выполнения и узких мест через Profiler.
- CUDA FP16, ONNX Runtime на CPU, INT8 для Linear на CPU и проверка доступности `torch.compile`.
- Автоматическое сравнение по скорости, пропускной способности или памяти GPU.
- Проверка численных отличий и точности на предоставленных размеченных данных.
- JSON, Markdown и CSV с реальными измерениями, настройками и версиями библиотек.
- Отдельный небольшой эксперимент обучения CNN в FP32 и AMP.
- Проверка изображений по одному, сравнение ответов двух моделей и запуск на своих файлах.
- Отдельная проверка локальных GGUF-моделей на CPU: скорость генерации текста,
  время до первого токена, память процесса и сравнение количества потоков.

Gemma и Ollama обсуждались как дальнейшее развитие. Их поддержка **пока не реализована**.

## Установка на Windows

Нужен Python 3.11 или 3.12. Открой PowerShell:

```powershell
git clone https://github.com/lsimg/Kernelixx.git
cd Kernelixx
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install --upgrade pip
.\.venv\Scripts\python.exe -m pip install torch==2.9.1+cpu torchvision==0.24.1+cpu --index-url https://download.pytorch.org/whl/cpu
.\.venv\Scripts\python.exe -m pip install -e ".[onnx,dev]"
.\.venv\Scripts\python.exe -m kernelixx system-info
```

Для совместимой видеокарты NVIDIA вместо CPU-сборки используй CUDA-сборку:

```powershell
.\.venv\Scripts\python.exe -m pip install torch==2.9.1+cu128 torchvision==0.24.1+cu128 --index-url https://download.pytorch.org/whl/cu128
.\.venv\Scripts\python.exe -m kernelixx system-info
```

Проверяй `cuda_available`: обнаруженная драйвером видеокарта ещё не означает,
что установленный PyTorch умеет выполнять вычисления на ней. При недоступной
CUDA программа переходит на CPU и сообщает об этом.

Основное имя пакета и команды — **kernelixx**. После переименования проекта
переустанови его через `pip install -e ".[onnx,dev]"` и используй новые команды.

## Первый эксперимент

Измерить обычную модель и посмотреть, помогает ли ONNX:

```powershell
.\.venv\Scripts\python.exe -m kernelixx benchmark --model resnet18 --weights default --device cpu
.\.venv\Scripts\python.exe -m kernelixx auto-optimize --model resnet18 --weights default --device cpu --methods onnx quantization --output results/my-first-run
.\.venv\Scripts\python.exe -m kernelixx compare --run-dir results/my-first-run/latest
```

`--weights default` использует готовые обученные веса. При первом запуске они
могут скачиваться. Без этого параметра встроенные модели имеют случайные веса:
это подходит для проверки выполнения, но не доказывает качество распознавания.
Без размеченного набора программа не измеряет настоящую точность.

Последняя команда читает уже сохранённый результат и не повторяет измерения.

## Команды

| Команда | Для чего |
|---|---|
| `system-info` | Проверить оборудование и библиотеки |
| `analyze` | Проанализировать модель и операции |
| `benchmark` | Измерить исходное выполнение |
| `optimize --method onnx` | Проверить конкретное преобразование |
| `auto-optimize` | Сравнить несколько способов и выбрать подходящий |
| `compare --run-dir ...` | Прочитать сохранённый отчёт |
| `train-benchmark` | Небольшой эксперимент FP32/AMP обучения |
| `gguf-benchmark --model-file ...` | Проверить локальную GGUF-модель на CPU |

Справка с параметрами:

```powershell
.\.venv\Scripts\python.exe -m kernelixx --help
.\.venv\Scripts\python.exe -m kernelixx auto-optimize --help
```

## Как читать результат

| Надпись | Значение |
|---|---|
| `baseline` | Исходная модель |
| `Median ms` | Типичное время одного запуска; меньше — лучше |
| `p95 ms` | Примерно 95% запусков заняли не больше указанного времени |
| `Samples/s` | Количество примеров в секунду; больше — лучше |
| `Speedup` | Отношение задержек; 2 означает вдвое быстрее, 0.8 — медленнее |
| `PASS` | Проверка прошла по заданным правилам |
| `rejected` | Преобразование отклонено, например из-за отличия ответов |
| `skipped` | Способ недоступен в этой среде; причина указана рядом |
| `Selected` | Выбранный вариант; может остаться `baseline` |

Размер весов и пиковая память во время выполнения — разные величины.
Пиковая память CPU сейчас не измеряется. Для CUDA показаны выделения PyTorch,
а не всё потребление видеокарты всеми программами.

## Проверка на настоящих фотографиях

Подготовить документированный набор из 200 изображений и измерить модель:

```powershell
.\.venv\Scripts\python.exe -m examples.prepare_imagenette --download --samples 200
.\.venv\Scripts\python.exe -m kernelixx auto-optimize --model resnet18 --weights default --device cpu --methods onnx quantization --dataset results/datasets/imagenet-val-resnet18-200.npz --output results/real-photos
.\.venv\Scripts\python.exe -m examples.inspect_predictions --dataset results/datasets/imagenet-val-resnet18-200.npz
```

Имена файлов, правильные классы, подготовка данных и контрольные суммы сохраняются.
Используются исходные ImageNet validation-файлы, найденные в архиве Imagenette.
Набор небольшой и не представляет полный ImageNet или любую будущую задачу.

Для своих файлов:

```powershell
.\.venv\Scripts\python.exe -m examples.predict_images --images "C:\Pictures\apple.png" "C:\Pictures\dog.jpg"
```

Замени пути на существующие фотографии. Программа покажет ответы обеих моделей,
сохранит пять наиболее вероятных классов и картинку с сопоставлением. Имена классов
фиксированы обучением на ImageNet. Например, `Granny Smith` не подтверждает сорт
красного яблока. Без точных подписей процент точности не вычисляется.

## Полученные результаты

Все цифры ниже относятся к конкретным локальным измерениям:

- ResNet18 на CPU: ONNX сократил медиану с 102.944 до 52.561 мс, сохранив 131/200
  правильных ответов и пройдя численную проверку.
- ResNet50 на CPU: ONNX сократил медиану с 216.445 до 131.811 мс, сохранив 155/200
  правильных ответов и пройдя численную проверку.
- ResNet50 исправила 30 ошибок ResNet18 и допустила шесть новых. Это сравнение
  готовых конфигураций с разными весами и подготовкой входа.
- При обработке по восемь изображений вместо одного повторные CUDA-эксперименты
  дали медианный коэффициент пропускной способности 4.647. Это не ускорение ответа
  для одной картинки: время обработки всей группы и расход памяти выросли.
- FP16 и INT8 иногда уменьшали память или меняли скорость, но были отклонены
  численной проверкой. Эти отрицательные результаты сохранены.
- SmolLM2-135M-Instruct Q4_K_M на CPU: при четырёх потоках вместо одного
  медианное время ответа сократилось с 522 до 242 мс, скорость генерации выросла
  с 58.8 до 118.6 токена/с. Ответы совпали, память процесса немного выросла.

## Проверка своего файла GGUF

GGUF — формат уже подготовленных весов текстовой модели. Для него используется
отдельный модуль запуска, потому что обычные методы PyTorch к такому файлу напрямую
не применяются. Установи готовый CPU-модуль:

```powershell
.\.venv\Scripts\python.exe -m pip install --only-binary=:all: --extra-index-url https://abetlen.github.io/llama-cpp-python/whl/cpu "llama-cpp-python>=0.3.36,<0.4" "psutil>=5.9"
.\.venv\Scripts\python.exe -m pip install -e ".[gguf]"
.\.venv\Scripts\python.exe -m kernelixx gguf-benchmark --model-file "C:\Models\SmolLM2-135M-Instruct.Q4_K_M.gguf" --threads 1 4 --output results/smollm2-gguf-cpu
.\.venv\Scripts\python.exe -m kernelixx compare --run-dir results/smollm2-gguf-cpu/latest
```

Замени путь на существующий файл. Здесь проверяется выполнение на процессоре,
видеокарта не используется. Сравниваются одинаковые вопросы и последовательности
токенов — фрагментов текста, которые модель выдаёт по очереди. Это проверка
совпадения ответов при разных настройках, а не оценка правильности ответов.
Память процесса показана отдельно от размера файла и памяти GPU.

Файл Q4_K_M уже квантован. Экономия от квантования в этом опыте не измерялась:
для этого нужна исходная версия той же модели. Все параметры, тексты ответов
и ограничения находятся в [отчёте SmolLM2](docs/GGUF_SMOLLM2.md).

[Русский аналитический разбор](docs/GGUF_ANALYSIS.ru.md) объясняет результат по
каждому вопросу и показывает, какие следующие проверки обоснуют рекомендации:
повторяемость, подбор потоков, длина текста, содержание и формат ответов, память
и сравнение одинаковых исходных весов в разных форматах точности.

Подробности: [валидация](docs/VALIDATION.md), [эксперименты](docs/REAL_IMAGE_VALIDATION.md),
[сравнение моделей](docs/MODEL_COMPARISON.md), [повторные запуски](docs/REPEATABILITY_VALIDATION.md).

## Этапы разработки и изменения

Разработка прошла от CLI и анализа модели к оптимизациям, автоматическому выбору,
валидации, отчётам, эксперименту обучения и установочным проверкам. Затем добавлены
реальные данные, исправления подготовки набора и вычисления порога accuracy,
batching, повторные парные измерения, просмотр ошибок и свои изображения.

[Полная история](docs/DEVELOPMENT_HISTORY.md) объясняет каждый этап, причины
изменений, измеренные результаты и ограничения. [Архитектура](docs/ARCHITECTURE.md)
показывает, какой модуль за что отвечает и как проходит один эксперимент.

Исходные фотографии, веса, окружения и рабочие `results/` остаются локально.
В публичном репозитории находятся код, тесты, документация и обезличенные копии
численных отчётов. Лицензия проекта — [MIT](LICENSE).
